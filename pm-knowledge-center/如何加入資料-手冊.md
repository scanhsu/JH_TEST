# 如何加入資料 — 投稿手冊（Contribution Guide）

| 你要加的資料 | 放的位置 | 用的範本 |

| **CPU / SoC 方案、vendor roadmap 情報** | `02-cpu-soc-roadmap/` | 已有 Intel / AMD / Arm / 網通四頁直接補；新 vendor 用 [`_template-platform.md`](./02-cpu-soc-roadmap/_template-platform.md) |

拿不定主意就放 `01-product-knowledge/`，之後再搬。

## 第二步：選一種加入方式

### 方式 A：丟給 Claude 整理（最省力，推薦）

適合：手上有現成資料（簡報、Excel、規格書），不想自己排版。

1. 開 Claude Code 對話，**上傳檔案或貼上文字**，講清楚要放哪一區。例句：
   - 「這是 XX-1234 的規格書和 kick-off 簡報，幫我建一個 03 產品案例」
   - 「這份 vendor roadmap 簡報，幫我更新 02 的 Intel 頁」
   - 「幫我把這篇筆記整理成 01 的知識分享頁」
2. Claude 會照範本寫成頁面、更新索引表、commit 並 push。
3. 到 GitHub 上檢查結果，有要改的再講。

⚠️ **NDA / 機密資料**：不要請 Claude（或任何人）把 NDA 內容寫進本庫。只放「一句話可公開摘要 + 內部存放位置 + 取得窗口」。

### 方式 B：GitHub 網頁直接編輯（適合小量新增、改幾行字）

**補充現有頁面**（例：在 02 加一筆評估紀錄）：

1. 進 [GitHub repo](https://github.com/scanhsu/JH_TEST) → `pm-knowledge-center/` → 點開目標 `.md` 檔
2. 按右上角 **鉛筆圖示（Edit）**
3. 在表格加一列或把 `📝 待補充` 換成實際內容
4. 更新頁面頂端的「最後更新」日期
5. 最下方按 **Commit changes**

**新增一頁**（例：建一個產品案例）：

1. 打開該區的 `_template-*.md`，全選複製內容
2. 回到該區資料夾 → **Add file → Create new file**
3. 檔名照規則取（見下方「命名規則」）
4. 貼上範本、填寫內容 → **Commit changes**
5. 回到該區 `README.md`，用鉛筆在索引表格**加一列連結**（格式：`[標題](./檔名.md)`）

**上傳附件**（簡報 / PDF）：

1. 進該區的 `attachments/` 資料夾（沒有就在 Create new file 時檔名前加 `attachments/` 建立）
2. **Add file → Upload files** → 拖入檔案 → Commit
3. 在相關 `.md` 頁面加連結：`[檔名](./attachments/檔名.pptx)`

### 方式 C：Clone 到本機編輯（適合大量整理、一次加很多頁）

```bash
git clone https://github.com/scanhsu/JH_TEST.git
cd JH_TEST/pm-knowledge-center
# 用 VS Code / Typora 等編輯器新增或修改 .md 檔
git add .
git commit -m "新增 XX-1234 產品案例"
git push
```

Markdown 不熟的話，用 VS Code 開檔案按 `Ctrl+Shift+V` 可以即時預覽。

## 第三步：照檢查清單收尾

每次投稿完成前確認：

- [ ] 頁面頂端有「最後更新日期」與「維護人（或作者）」
- [ ] 該區 `README.md` 的索引表有加上這一頁
- [ ] 沒有把 NDA / 機密內容、實際單價、客戶未公開資訊寫進來（只放內部存放位置連結）
- [ ] 引用其他頁面時用相對連結（`../02-cpu-soc-roadmap/intel.md`），點得開
- [ ] 如果補完了[待補清單](./待補清單-TODO.md)上的項目，把該項 `[ ]` 改成 `[x]`

## 各類資料要準備什麼內容

### 加「產品案例」（03）— 最有價值的投稿

規格表 PLM 系統都查得到，這個庫的價值在**決策理由和教訓**。要準備：

- 基本：型號、年份、目標市場、定價帶
- 規格摘要：CPU / 記憶體 / 儲存 / 網路 I/O / 電源 / 散熱 / 認證
- **核心內容**：當時為什麼選這個平台？放棄了什麼替代方案、為什麼？成本結構大概比例？開發中踩過什麼坑（Lesson & Learn）？
- 就算只記得大概，寫下來也比空白有用；執行面細節可請當時的 PJM 補充。

### 加「方案 / roadmap 情報」（02）

- 公開資訊：直接補進世代整理表、選型筆記
- NDA roadmap：只在「Roadmap 追蹤」表加一列 —— 日期、來源、一句話可公開摘要、內部存放位置
- 評估過的平台：在「評估紀錄」表留結論，**沒採用也要寫原因**（這對下次選型最有用）

### 加「知識分享」（01）

- 用範本的結構：TL;DR 三行講完重點 → 背景 → 內容 → 對 PLM 工作的影響
- 有原始簡報就放 attachments 並連結

## 常見問題

**Q：我寫的東西不確定對不對，可以發嗎？**
可以。在不確定的地方標 `（待確認）`，發出來讓其他人修，比放在自己硬碟裡有用。

**Q：改壞了怎麼辦？**
Git 有完整版本紀錄，任何頁面都能還原，放心編輯。

**Q：中文檔名可以嗎？**
內容頁建議用英文小寫加連字號（跨系統相容性好）；但像本手冊、待補清單這類入口文件用中文檔名方便辨識，兩者並存沒問題。

**Q：想大改結構（增刪整個分區）？**
先在團隊會議或跟知識庫維護人討論，再動手。
